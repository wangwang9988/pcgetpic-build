## 复核同事「执行后」汇报（同日 08:45，已产出可转发文字）

改动已落地在工作区（store + tuget-website + deploy/nginx，git status 全为 M，未提交）。逐项核对结论：

- **P0 实测缺陷**：`store/index.html` 预取写的是 `?product=downpictures`，但 server 的 products 表只有 `dangtu`/`tuget`（`normalizeProductCode` + `getProduct` 校验），`curl` 实测返回 404 `PRODUCT_NOT_FOUND` → store 的 head 预取**永远失败**，`fetchPackages()` 每次都回退到 axios（无 product，走 dangtu 默认）。即"0ms 并行预取"未生效，且每次访问多一次 404。
- **P1**：nuxt.config.ts 的 `prerender:generate` 注入脚本里，`f.apply(window, arguments)` 写在 `.then(function(r){…})` / `.catch(function(){…})` 内部，`arguments` 是内层函数的（[r]/[err]）而非 fetch 入参 → messages.json 一旦 404/失败，fallback 变成 `fetch(Response)` 直接抛错，语言包加载硬失败（非降级）。且 hash 用 `i18nLocaleHash` 复制品另算一遍，与模块 `computeLocaleHashes` 是两套实现，升级/改路径即静默失配。
- **P1**：`bundle.dropMessageCompiler: true` 当前安全（三语 JSON 里 `{}` 插值 0、`|` 复数 0、`@:` 链接 0），但生产构建下编译器缺失时 `compile()` 直接 `() => message` 原样返回、无任何 warn → 以后谁写 `{count}` 线上就露花括号。建议加构建期断言。
- **数据核对**：store dist 314,575 B raw（index 235,935 + vendor-vue 78,640）/ 108,916 gz，`resolveComponent` 0 处，12 个 .gz 已生成；tuget /buy/ modulepreload 344,194 B（336.1KB），`DQ0B-vVY.js` 33,580。均与汇报一致。
- **新发现**：tuget entry 由 158,835/54,601 gz 变为 180,502/63,136 gz（+8.5KB gz），与 dropMessageCompiler 预期方向相反（疑似 chunk 边界把原 Bv2cXxmn 34.6KB + yvjg20B- 14KB 并进 entry），营销页也吃这份 entry，需复核 LCP。
- **nginx nit**：`expires 1y` + `add_header Cache-Control` 会输出两条 Cache-Control；location 内一旦有 add_header，server 级 HSTS / X-Content-Type-Options 不再继承（/assets/、/_nuxt/、/_i18n/ 均受影响）。
- 做对的点：骨架屏替代写死价格；`import.meta.client` 守卫使 setup 期 loadPackages 不会在预渲染时把价格烘进 HTML/payload。

## 评审「/buy/ 首屏 + 支付宝二维码秒出方案」（tuget_checkout_performance_plan.md）

同事新方案（`~/.gemini/antigravity-ide/brain/a4681afd.../tuget_checkout_performance_plan.md`）已逐条核对代码与构建产物，产出可转发意见。核实结论：

- **二维码那条是真缺陷**：`PaymentCheckout.vue:271-280` 的 `watch(creatingOrder)` 确实在网络请求第 0ms 就切到 payment 态，`order=null`、`qrDataUrl=''` → 空白方块转圈吃满网关 RTT。删掉它、改成 `createOrder()` 返回后再切页即可。
- **方案对 store 的机制描述是错的**：store 并没有"切页前预生成二维码"。`store/src/views/home/components/PaymentQRCode.vue:348` 静态 `import QRCode`，在组件 `watch(orderData.qr_code, {immediate:true})` + `await toDataURL(width:240)` 里生成；`Home.vue:516-520` 只是 requestIdleCallback 预热组件 chunk。store 快的原因仅仅是「在表单页等完了网关」。→ 只删 watch 就能拿到 90% 效果，4.1.2 的提前 await 是加分项且**有回归风险**（fire-and-forget 改 await 后 toDataURL 抛错会落进 createOrder 外层 catch → order 置 null 返回 false → 订单已建/券已占但用户看到"下单失败"）。
- **width 408→240 是退步**：显示尺寸 200/210px，408 是为 2x DPR 准备的；toDataURL 408px 实测几毫秒，省不出 0.5s。
- **首屏数字全对但对比基准错**：10 chunk / 344,194 B / 126.4KB gz / messages.json 55,700 B / _payload.json 69 B 均核实无误；但 store 首屏不是"1 个文件 77.7KB gz"——`dist/index.html` 同时 modulepreload 了 `vendor-vue`(78,640 B / 31.3KB gz)，合计 109KB gz。真实差距 17KB gz（约 16%），撑不起 1.8s→400ms。
- **碎片合并/ payload 是化妆**：71+84+354=509 B；`<link rel=preload as=fetch>` 与 JS 并行、不是串行 RTT。
- **messages.json 这条有坑**：删 head 预取≠省 55KB。`CxMbXubB.js` 里含 `loadMessages` + `_i18n/${...}` 拼接，i18n 插件在 hydration 时仍会拉 zh-CN 消息，head 脚本只是把请求提前并行；删掉可能变成 hydration 才发起（更慢）。
- **方案 B 成本两头估错**：说"只需一套 Vite 配置"低估（部署/canonical/JSON-LD/sitemap/埋点/多语言路由）；但收银台本不该被索引（现全局 robots=index,follow 且 /buy/ 带 JSON-LD），若确定 noindex，SEO 损失不成立 → 属产品决策。
- **遗漏的现存 bug**：`qr_code` 为空（支付宝降级走 Stripe）时占位符永久转圈无任何提示，改完提前切页后更显眼。
- **验证计划漏洞**："modulepreload ≤3" 会假通过；store 有 `ENTRY_GZIP_BUDGET_BYTES` 构建期守门、tuget 没有；二维码"肉眼验收"应换 performance.mark 埋点。方案里 `nitro.hooks.hook('prerender:generate')` 直接挂 config 是错的（现有写法是 `hooks: { 'nitro:init'(nitro) {...} }`），且 `didPrerenderHtml = true` 放在 /buy/ early return 之后会让 close 断言失效。
